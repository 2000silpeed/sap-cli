Overview

이 프로젝트는 정확히 무엇인가

SAP GUI Scripting API를 CLI와 MCP로 감싸고, 그 위에 온톨로지, transcript, review planner, 역할 기반 tool surface를 얹어서 AI가 SAP를 더 안전하게 다루게 만드는 도구입니다.

1. 문제 정의

SAP 반복 업무는 여전히 사람 손에 많이 의존합니다. RPA는 유지보수 비용이 높고, ABAP은 리드타임이 깁니다. sap_cli는 이 사이에서 즉시 실행 가능한 자동화 층을 제공합니다.

2. 기술 정의

SAP GUI를 직접 조작하는 COM wrapper 위에 dispatcher를 두고, CLI/MCP/Shell/Daemon이 모두 같은 실행 경로를 타게 설계했습니다.

3. 전략 정의

목표는 “AI가 SAP를 만진다”가 아니라 “AI가 만져도 추적 가능하고, 검토 가능하고, 역할별로 봉쇄 가능한 시스템”을 만드는 것입니다.

              FAQ
              
자주 생기는 질문

            

          

          

            온톨로지가 있는데 왜 transcript가 또 필요한가
            
온톨로지는 구조 기억이고 transcript는 실행 기억입니다. 온톨로지는 “원래 이 트랜잭션이 어떻게 생겼는가”를 설명하고, transcript는 “방금 무엇을 했고 어떤 결과가 나왔는가”를 설명합니다.

          

          

            transcript-plan은 실제로 재실행하나
            
아닙니다. 실제 실행이 아니라 재실행 전에 무엇을 확인해야 하는지와 위험도를 계산하는 review 도구입니다.

          

          

            왜 operator와 verifier를 굳이 나누나
            
AI 운영에서는 프롬프트로 금지하는 것보다 tool surface 자체를 줄이는 것이 더 안전합니다. verifier는 mutating tool 없이도 충분히 사후 검토를 수행할 수 있습니다.

          

          

            사람이 직접 쓸 때도 이 구조가 의미가 있나
            
개인 자동화 도구로만 쓰면 일부는 과할 수 있습니다. 하지만 MCP와 agent를 붙일 계획이라면 dispatcher, transcript, role surface는 거의 필수에 가깝습니다.

          

          

            가장 먼저 검증할 명령은 무엇인가
            
sap connect, sap session, sap screen입니다. 이 세 개가 안정적이면 나머지 기능 검증이 훨씬 쉬워집니다.

          

          

            온톨로지와 BusinessProcess의 차이는
            
온톨로지는 트랜잭션 1개의 화면/필드/액션 구조를 저장합니다. BusinessProcess는 여러 트랜잭션을 연결한 업무 흐름을 구조화합니다. 예를 들어 자재 조달은 MM01→ME21N→MIGO→MIRO 4개 트랜잭션의 연결이며, 앞 스텝의 출력(자재번호)이 뒤 스텝의 입력으로 자동 연결됩니다.
